# PRD: LLM Output Guardrails

**Feature**: 004-output-guardrails | **Date**: 2026-07-03

---

## Problem Statement

The AI chatbot agent service streams LLM responses directly to the user's browser via SSE with no output-side safety validation. While input guardrails validate what the user sends to the LLM, the LLM's own output is unfiltered. This creates two critical risks:

1. **PII Leakage**: The LLM may hallucinate or regurgitate PII (email addresses, phone numbers, passport numbers, credit card numbers) from its training data, conversation context, or tool results that somehow bypassed the structural exclusion in the agent gateway.

2. **Harmful Content**: The LLM may generate toxic, inappropriate, policy-violating, or prompt-injection-artifact content that reaches the user's screen in real time.

The current system has a "blind spot" — the path from LLM output to user display has zero safety checks. Every token generated by the model is streamed directly to the browser.

## Solution

Add a guardrail pipeline between the LLM token stream and the SSE output that validates every piece of LLM-generated text before it reaches the user. The pipeline:

1. **Accumulates tokens into sentences** — splits at sentence boundaries so the guardrail sees complete semantic units, not meaningless token fragments.
2. **Validates through two layers** — a fast regex PII scanner (~1ms) catches structured PII patterns, then a NeMo/Mimo safety classifier (~100-300ms) catches nuanced harmful content.
3. **Checks across sentence boundaries** — a sliding window overlaps consecutive chunks to catch PII that spans two sentences.
4. **Hides latency with pipelining** — validates the next chunk while streaming the current one, so users experience minimal delay after the first sentence.
5. **Hard-stops on violations** — kills the stream immediately, sends a clear error message, saves the safe partial response, and logs a security event.

From the user's perspective: safe conversations feel the same. Unsafe responses are cut off with a clear "Response was blocked for safety reasons" message. The user's conversation context is preserved up to the last safe sentence.

## User Stories

1. As a **traveler**, I want the chatbot's responses to be checked for sensitive information before I see them, so that I'm never exposed to leaked PII like credit card numbers or passport details.

2. As a **traveler**, I want safe responses to stream smoothly without noticeable delays, so that output safety checks don't degrade my chat experience.

3. As a **traveler**, I want to see a clear error message when a response is blocked, so that I understand something went wrong without being confused by a silent failure.

4. As a **traveler**, I want my conversation history preserved even when a response is blocked, so that I don't lose context from the safe part of the conversation.

5. As a **traveler**, I want the chatbot to never show me harmful, toxic, or inappropriate content, so that the chat experience feels safe and professional.

6. As a **traveler**, I want the safety system to catch PII even when it's split across two sentences, so that clever phrasing by the LLM can't bypass the safety checks.

7. As a **system operator**, I want structured logs for every guardrail check (pass or fail), so that I can monitor block rates and identify patterns in guardrail triggers.

8. As a **system operator**, I want security event logs that record which guardrail rule triggered without including the blocked content, so that I can investigate incidents without creating a secondary PII exposure in logs.

9. As a **system operator**, I want a kill switch to disable output guardrails without code changes, so that I can rapidly respond to false positive issues in production.

10. As a **system operator**, I want configurable guardrail parameters (overlap window size, max chunk size, NeMo timeout), so that I can tune the pipeline for different deployment environments.

11. As a **system operator**, I want the guardrail pipeline to fail closed when the safety classification service is unavailable, so that unvalidated content never reaches users even during service outages.

12. As a **developer**, I want tool call/result events to bypass the output guardrail, so that structured data from the PII-stripped gateway isn't double-checked unnecessarily.

13. As a **developer**, I want the output guardrail pipeline to handle code blocks correctly (not splitting at `.` inside code), so that technical responses aren't incorrectly chunked.

14. As a **developer**, I want the sentence boundary detector to handle abbreviations, decimal numbers, and URLs without false splitting, so that chunks always represent complete semantic thoughts.

15. As a **developer**, I want the regex PII scanner to reuse the existing patterns from the input-side PII scrubber, so that PII detection rules are maintained in one place.

16. As a **security engineer**, I want every chunk to pass both regex PII scanning AND NeMo safety classification before reaching the user, so that both structured and unstructured threats are caught.

17. As a **security engineer**, I want the hard stop to be immediate — no "redact and continue" — so that surrounding context can't reveal blocked information through inference.

18. As a **security engineer**, I want boundary PII detection via a sliding window, so that PII split across sentence boundaries (e.g., name in one sentence, card number in the next) is caught.

19. As a **QA engineer**, I want the pipeline to be testable with mock NeMo responses, so that I can write deterministic tests without depending on a live LLM classification endpoint.

20. As a **QA engineer**, I want test scenarios for each PII type (email, phone, passport, credit card) in LLM output, so that guardrail coverage is comprehensive and verifiable.

## Implementation Decisions

### Sentence-Boundary Chunking

LLM output tokens are accumulated in a buffer and split into chunks at sentence boundaries (`.`, `!`, `?`, `\n` followed by whitespace + uppercase or end-of-stream). This ensures the guardrail always receives complete semantic units. A heuristic handles edge cases: code blocks (triple-backtick fences) are accumulated as single chunks, abbreviations (`Dr.`, `Mr.`) don't trigger splits, and decimal numbers (`$1,234.56`) are preserved. A configurable max chunk size (default 200 tokens) force-splits excessively long sentences.

### Pipeline Parallelism

While chunk N is being streamed to the user via SSE, the guardrail check for chunk N+1 runs concurrently using `asyncio.Task`. This hides the ~100-300ms NeMo classification latency for all chunks after the first. The first chunk has unavoidable latency.

### Cross-Chunk Sliding Window

A configurable window (default 30 tokens) of the previous chunk's tail is concatenated with the current chunk's head to form an overlap region. The regex PII scanner runs on this overlap region before the main chunk check. This catches PII patterns that span sentence boundaries.

### Layered Guardrail Execution

Two layers run sequentially on every chunk:
1. **Regex PII Scanner** (~1ms): Pattern-matches email, phone, passport, credit card. Also runs on the sliding window overlap region. If this fails → hard stop immediately, NeMo skipped.
2. **NeMo Output Rail** (~100-300ms): Calls the Mimo safety classification endpoint with an output-specific system prompt. Catches harmful content, toxicity, prompt injection artifacts, subtle PII references. Only runs if regex passes.

### Hard Stop Behavior

On any guardrail failure at any layer:
1. Stop consuming tokens from the LLM
2. Send SSE error event: `{"code": "OUTPUT_GUARDRAIL_BLOCKED", "message": "Response was blocked for safety reasons.", "partialMessageId": "<uuid|null>"}`
3. Persist partial response (safe chunks before the block) to NestJS via batch message endpoint
4. Log structured security event with guardrail layer and rule — never the blocked content

Redact-and-continue was explicitly rejected: surrounding context can still reveal the sensitive information through inference.

### GuardrailService Protocol Extension

The existing `GuardrailService` protocol gains a new `validate_output_chunk(chunk: str) -> Tuple[bool, str]` method. The `NemoGuardrailService` implements this with an output-specific system prompt for safety classification.

### SSE Contract Extension

A new error code `OUTPUT_GUARDRAIL_BLOCKED` is added to the existing `error` event type. No new SSE event types are introduced. The `token` event now carries sentence-sized content (not single tokens) when output guardrails are enabled — this is backward compatible.

### Configuration

Four new environment variables control the pipeline:
- `OUTPUT_GUARDRAIL_ENABLED` (bool, default true) — kill switch
- `OUTPUT_GUARDRAIL_OVERLAP_TOKENS` (int, default 30) — sliding window size
- `OUTPUT_GUARDRAIL_MAX_CHUNK_TOKENS` (int, default 200) — force-split threshold
- `OUTPUT_GUARDRAIL_NEMO_TIMEOUT` (float, default 2.0) — NeMo API timeout

## Testing Decisions

### Testing Philosophy

Tests should verify **external behavior** — what the pipeline emits and what errors it raises — not internal implementation details like buffer state or window contents.

### Testing Seams

1. **OutputGuardrailPipeline** (primary seam): Feed tokens in, assert chunks out or errors raised. Mock the NeMo service to control classification results deterministically.
2. **ChunkBuffer** (unit seam): Feed tokens, assert sentence boundary detection. Pure function — no mocks needed.
3. **SSE endpoint** (integration seam): Send chat messages, observe SSE events for guardrail behavior. Highest-level seam.

### Modules to Test

- **ChunkBuffer**: Sentence boundary detection, code fence handling, max chunk size, abbreviation/decimal/URL edge cases
- **SlidingWindow**: Overlap region construction, window update on chunk transition
- **OutputGuardrailPipeline**: End-to-end token → chunk → guardrail → emit/block flow. Parameterized across PII types.
- **NeMo output rail**: SAFE/UNSAFE classification, timeout handling, fail-closed behavior
- **SSE integration**: `OUTPUT_GUARDRAIL_BLOCKED` error event emission, `partialMessageId` population

### Prior Art

- Existing input guardrail tests in `apps/agent/tests/` — same mock pattern for NeMo service
- Existing PII scrubber tests — same regex patterns, inverse usage (detect vs. scrub)
- SSE streaming tests — same `EventSourceResponse` assertion pattern

## Out of Scope

- **Frontend typewriter animation**: Sentence-boundary chunking produces bursty text arrival. Smoothing this with a character-by-character animation is a frontend concern, documented as a future enhancement.
- **Custom Colang rules**: No standalone NeMo Guardrails server with Colang 2.0 rule files. The Mimo classification endpoint approach is sufficient.
- **Output guardrails for tool events**: Tool call/result events contain structured, PII-stripped data from the gateway. They bypass the output guardrail pipeline.
- **ML-based PII detection**: Regex patterns cover the required PII types. Upgrading to ML-based NER (spaCy, Presidio) is deferred.
- **Distributed pipeline coordination**: Single-instance deployment assumed. No cross-process state sharing.
- **Rate limiting NeMo output calls**: API budget monitoring is an operational concern addressed by the existing Observability principle, not a feature requirement.

## Further Notes

- The output guardrail pipeline is the symmetric counterpart to the existing input guardrail. Together they form a complete safety envelope: user message → input guardrail → LLM → output guardrail → user display.
- The `pii_scrubber.py` regex patterns are reused for detection (not scrubbing). This ensures PII detection rules are maintained in a single location. If new PII patterns are added to the scrubber, they automatically apply to output guardrail detection.
- The architecture decision to reject "redact and continue" in favor of hard stop is a security-critical choice. It prevents information leakage through inference from surrounding context. This decision was made during the grilling session and is documented in `research/output-guardrails-architecture.md`.
- Pipeline parallelism implementation uses `asyncio.Task` with a one-chunk lookahead. This is intentionally simple — more complex prefetching would add complexity without meaningful latency benefit given the single NeMo call per chunk.
